Improve: **$ARGUMENTS**

If I named a dimension to optimize for, that one wins over everything else. If not, optimize for clarity and say so.

Before changing anything, state in one line: **what this is currently optimizing for, and what it's trading away.** Most things are already optimized for something — usually by accident. Name it before you disturb it.

Then:

1. **Deliver the improved version in full.** Not a description of improvements. The actual thing, ready to use.
2. **Then a short changelog** — what changed and why, one line each. Enough that I can reject any single change without unpicking the rest.

Rules of engagement:

- **Preserve intent absolutely.** You're improving execution, not substituting your own judgment about what this should be.
- **Every change earns its place.** If a change is neutral, don't make it. Churn disguised as improvement is worse than leaving it alone.
- **Keep what works.** Explicitly note anything you deliberately left untouched, so I know it was a decision and not an oversight.
- **Flag anything you'd change but can't** — because it needs a decision, a fact, or access you don't have.

If the thing is already good, say so and make only the changes that genuinely help. A short changelog is a legitimate result.
